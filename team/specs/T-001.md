## Problem
The demo (MISSION.md "Current goal") is: hold Space, ramble ~20 s, release, and
see a polished Markdown note with visible, honest latency numbers. Today the
right pane shows a static "Polishing…" placeholder until the LLM Gateway has
returned the *whole* completion (`POST /api/polish` in `app.py` waits for the
full JSON response; `stop()` in `static/index.html` renders it in one go). For a
~20 s ramble the viewer watches a blank pane for the entire LLM round trip.

HYPOTHESIS: showing the first polished words as soon as the model emits them
makes the app feel substantially faster on camera, even though total time is
unchanged. Evidence: none (MISSION.md "Evidence we have: None yet"); this is the
owner's #1 priority on the 2026-09-27 improvement list. Cheapest test: the owner
records one take before and one after and judges the footage.

Feasibility: AssemblyAI documents that the LLM Gateway supports `stream: true`
on `/v1/chat/completions`, returning an OpenAI-compatible Server-Sent Events
stream (source: assemblyai.com/blog/stream-llm-responses-voice-pipeline-tool-calling-structured-outputs-real-time-actions,
assemblyai.com/docs/llm-gateway/quickstart). Not verified live: there is no API
key in the agent environment.

## Outcome
The polish endpoint streams the polished text as the LLM produces it. The owner
can watch the chunks arrive with one live `curl -N` using their key. The app
works exactly as it does today, but its "AI polish" and "Stop → polished"
badges are now timed in the browser. (What the user sees on screen does not
change until T-005.)

## Acceptance criteria
All criteria must be verifiable without an AssemblyAI key. Backend criteria are
checked with `httpx.MockTransport` in pytest (QA's locked tests in
`tests/acceptance/`). Browser criteria are named checks in
`scripts/e2e_check.py`, using the fake mic, the fake socket, and a text/plain

Backend (pytest, mocked upstream):
- [ ] Given a non-empty transcript, when the browser requests a polish, then the request the server sends to the LLM Gateway asks for a streamed completion (`"stream": true`) and still contains the unchanged system prompt, the transcript as the user message, the configured model, and the server-side API key.
- [ ] Given the mocked gateway streams an SSE response whose deltas are "**Launch", " update**", "\n\n- Friday" followed by `[DONE]`, when the polish response body is read to the end, then the concatenated text the browser receives is exactly "**Launch update**\n\n- Friday" (no SSE framing, no `[DONE]`, no JSON).
- [ ] Given the mocked gateway returns a normal non-streamed JSON completion (fallback: the gateway ignored `stream`), when a polish is requested, then the browser receives the full completion text, with no error.
- [ ] Given the gateway responds with a non-200 status (e.g. 401 "Invalid API key") before any text, when a polish is requested, then the server responds 502 with a detail containing the status code and upstream message (same behaviour as today).
- [ ] Given an empty or whitespace-only transcript, when a polish is requested, then the server responds 400 and makes no upstream call (unchanged).
- [ ] Given `ASSEMBLYAI_API_KEY` is unset, when a polish is requested, then the server responds 500 with a message naming `ASSEMBLYAI_API_KEY` and makes no upstream call.

Browser (named checks in `scripts/e2e_check.py`, plus a screenshot):
- [ ] Given the polish response is a plain-text Markdown body, when the dictation finishes, then the Polished pane shows that Markdown rendered (bold title, list items), just as it renders today. Existing check: `markdown rendered`.
- [ ] Given the polish body contains `<script>alert(1)</script>`, then no `<script>` element appears in the Polished pane. Existing check: `llm output html escaped`.
- [ ] Given the polish has completed, then the clipboard (auto-copy) holds exactly the full polished Markdown. The existing `auto-copied markdown` check is strengthened to equality.
- [ ] Given the polish has completed, then the "AI polish" badge (polish request sent → body fully read) and the "Stop → polished" badge (release → body fully read) each show a browser-measured integer followed by ` ms`. No badge shows a number supplied by the server. The existing `badges filled` check changes from `bLlm == "412 ms"` to "ends with ` ms`"; this is the only pre-existing check whose assertion changes, and the PR description must say so.
- [ ] All other pre-existing checks in `scripts/e2e_check.py` pass unchanged, and `./scripts/check.sh` exits 0 (outputs pasted in the Implementation notes).

## Tech plan
_Tech lead, 2026-09-27, part 1 of 2 (re-planned after the PM's split; supersedes my earlier whole-ticket plan). **Fits: Status → `planned`.**_

**Approach.** Change `POST /api/polish` in place so it returns `text/plain; charset=utf-8` streamed with `StreamingResponse`. There is no second endpoint, because the spec rules out a separate non-streaming mode.
- **Upstream call.** The server adds `"stream": true` and sends the request with `client.send(client.build_request(...), stream=True)`. That lets it look at the status and content-type *before* it commits to a 200.
- **Non-200.** `aread()`, then the existing `_upstream_error` 502.
- **200 but not `text/event-stream`.** This is the JSON fallback: parse `choices[0].message.content` exactly as today (including `.strip()` and the "Unexpected LLM Gateway response" 502), then return it as a one-chunk body.
- **SSE.** An async generator parses the stream the way AssemblyAI's own SDK does (`assemblyai/llm_gateway/v1/api.py::stream_completion`): ignore lines not starting with `data: `, stop at `[DONE]`, `json.loads` the rest, and yield each non-empty `choices[*].delta.content`. Role-only and usage chunks carry no content.
- **Cleanup.** A `finally` closes the upstream response and the client. If `client.send` itself raises (connect error or timeout), close the client and re-raise. Today's `async with` guaranteed this.
- **Browser.** It changes minimally. It times the polish request itself (`polishAt = performance.now()` before `fetch`). `!res.ok` → `(await res.json().catch(() => ({}))).detail || "Polish failed."`. Otherwise `polishedMarkdown = (await res.text()).trim()`, and an empty body throws `Polish failed.` (existing string); otherwise Copy would enable on an empty note, e.g. with a non-OpenAI `LLM_MODEL`. `bLlm` = `performance.now() - polishAt`. Everything else in `stop()` is unchanged.
- **Why not proxy raw SSE to the browser:** it would need a JS SSE parser, and backend criterion 2 requires plain text.
- **Why not `EventSource`:** it is GET-only and can't send the transcript.
- **Dependencies:** none new. `StreamingResponse` comes with FastAPI; `stream=True` and `aiter_lines` come with httpx.

**Risks.**
1. **The gateway's streaming format is unverified live.** The SDK itself says its parsing is "verified against OpenAI-routed models only". The default `gpt-5-mini` is OpenAI-routed. Another `LLM_MODEL` may yield no parseable lines → empty body → visible `Polish failed.`, not silent garbage. *How we'll know:* the owner's one live `curl -N`/take (question already open).
2. **Buffering.** Nothing in the app buffers (no middleware; uvicorn flushes each yield), but no mock can prove what reaches the browser incrementally. In part 1 this has no UI impact: the browser reads the whole body anyway. It matters for T-005.
3. **A mid-stream upstream error** happens after the 200 is sent. uvicorn aborts the connection, `res.text()` rejects, and the existing catch shows the browser's error message (e.g. "network error") in the banner and returns to idle. That's acceptable for part 1; T-005 adds the proper cut-off state. Don't write a pytest for it without `TestClient(raise_server_exceptions=False)`.
4. **Stale badges on a failed second take.** `bLlm`/`bTotal` from a previous take stay visible if the next polish fails. This is pre-existing behaviour; resetting at release is explicitly T-005. The numbers are still browser-measured, so criterion U4 holds.
5. **httpx timeout.** `Timeout(30, connect=5)` applies per read, so a long stream won't be cut off at 30 s total; a gap of more than 30 s between chunks would be. Same limit as today.
6. **An existing test changes.** `tests/test_app.py` edits one test. The guard doesn't flag this, but I'll check in review that nothing was weakened beyond the JSON-shape lines.
